# CCR v0.4.8

## Highlights

- CCR can launch Claude Code against a registered provider even when the user
  has no Claude subscription or Anthropic API authentication.
- Existing authenticated users keep the current side-by-side behavior: Claude
  authentication remains available while CCR aliases route through registered
  providers.
- Provider-only launches isolate Claude Code from inherited Anthropic and OAuth
  credentials and authenticate it only to CCR's loopback gateway.

## User-Visible Changes

`ccr launch` now uses `--auth-mode auto` by default. When Claude authentication
is available, auto mode resolves to `preserve` and retains the existing mixed
Claude subscription and registered-provider workflow. When Claude
authentication is unavailable and `--model <alias>` selects a routable CCR
model, auto mode resolves to `provider-only` and starts Claude Code through that
provider.

If neither Claude authentication nor an explicit startup alias is available,
CCR exits before starting the gateway, opening the runtime database, or
launching Claude Code. The error directs the user to run `claude /login` or
launch with a configured alias. Existing model aliases are suggested when CCR
can read them safely from the current database.

`--auth-mode provider-only` makes the isolated behavior explicit.
`--auth-mode gateway-token` remains accepted as a legacy-compatible spelling.
On macOS, automatic selection reads Claude Code's structured auth status so it
can distinguish a Keychain-backed login from a signed-out installation without
reading or exposing Keychain credentials.
Both modes require an explicit CCR startup alias. `preserve` and
`subscription-pool` retain their existing behavior.

Launch summaries and `ccr doctor` report the resolved authentication mode so
degradation is visible rather than implicit.

## Upgrade

```bash
brew upgrade hishamkaram/tap/claude-code-router
ccr version
ccr doctor
```

No database migration or provider reconfiguration is required. Existing launch
commands continue to preserve Claude authentication whenever it is detected.

## Privacy and Security

- Provider-only launches remove inherited Anthropic API keys, custom auth
  headers, OAuth access and refresh tokens, and OAuth scopes from the Claude
  Code child environment.
- Claude Code receives only a generated credential for CCR's loopback gateway;
  provider credentials remain inside CCR and are not forwarded to the child.
- Authentication detection never prints credential values. Detection failures
  conservatively retain `preserve` behavior so unavailable platform credential
  stores do not silently disable an existing Claude login.
- Provider secrets remain keychain-backed and are not stored raw in SQLite.

## Compatibility

- Environment-based Anthropic API-key and OAuth authentication, authenticated
  custom headers, and the current Claude credentials file are recognized.
- macOS Keychain-backed Claude sessions are detected through structured Claude
  CLI status; an unexpected status failure resolves conservatively to
  `preserve`.
- Provider-only routing works with registered routable aliases and does not
  change provider protocol translation or in-session `/model` behavior.
- The macOS computer-use helper remains a source-built unsigned preview and is
  not included in Homebrew or GoReleaser archives.

## Verification

Release evidence is recorded in `docs/acceptance/v0.4.8.md`, including launch
argument, environment, persistence, CLI, and live Claude Code provider-only
coverage.

## Known Limits

- Auto mode cannot infer a provider-only startup model. Users without Claude
  authentication must select a configured alias with `--model <alias>`.
- Credential-store detection is intentionally conservative: an unexpected
  detection error preserves authentication instead of forcing provider-only
  mode.
